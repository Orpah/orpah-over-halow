    限频口径：两侧与设备侧（哪些限、哪些不限、边界在哪）

    设备侧（客户端）自限频是「自愿」的，不是一道防线：一台被改过或失控的设备根本不会做它，协议也要求不了它。它的实际好处只有三个：空口是共享介质（Router 侧虽然会丢，但那些帧已经上过空口、带宽已经花掉）、每次上报都要花电（免电池设备最紧的就是这个）、别去撞上游的桶（撞上等于没被听见还添了流量）。所以它的语义是「延后」而不是丢弃（丢自己的报等于漏报，找人场景不可接受）——计数栏里的「已延后」下一拍还会发。页面上的「刷量」按钮模拟的就是一台失控设备，它明确绕过自限频；那正是这条边界的现场证据：绕过之后才轮到 Router/Server 的桶开始丢。

    §5.8 的限频分两处：Router 侧（网口上行）限带宽 —— 转发按 SN、未签名 REQ-CONNECT 按源 MAC；Server 侧限 CPU（ECDSA 验签之前）—— per-SN + per-Router（源地址），两条都过才放行。两边参数不同（Router 侧更宽）是有意的：两边都做窄，报文死在 Router 就看不出「哪道防线拦的」。边界照实说：per-SN 的 key 取自尚未验签的 sn，轮换 SN 就能绕过它；命中走失表的 REQ-CONNECT 与 ORPAH-FOUND 都不限（漏一条等于一个人没被找到）；全体一起被刷时各条防线都会到顶，那时只能靠上游/接入侧，限频不是“防住了”。刷量条数按服务端参数自动取。速度差照实说：仿真空口只有几 条/秒的吞吐，而两个桶补得比它快，所以页面上「轮换刷量」大致拦不下几条（不包装成演示效果）；要看两条线各拦一段，请看离线 demo_ratelimit.py（实测同一 SN 连发 200 条：Router 侧丢 159、Server 侧丢 35）。
